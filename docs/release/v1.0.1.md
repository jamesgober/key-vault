# v1.0.1 — Scratch Buffer Wipe and std Requirement

**Release date:** 2026-10-08
**Phase:** 1.0.1 (patch release)
**Status:** **stable.** The 1.0 contract in [`docs/STABILITY-1.0.md`](../STABILITY-1.0.md) is unchanged.

---

## Why this release exists

1.0.1 fixes a gap in how `KeyVault::with_key` clears recovered key
material, states the `std` requirement plainly instead of claiming
conditional `no_std` support, and drops an unused dependency. There
are no public API changes; `cargo semver-checks` against 1.0.0 reports
no semver update required.

---

## What's in 1.0.1

### Fixed: plaintext could remain in the scratch buffer if decoding failed or panicked

`KeyVault::with_key` rebuilds the key in a thread-local scratch buffer
and hands the caller a slice of it. A guard volatile-zeroes that buffer
when the call ends, but in 1.0.0 the guard was created only after
defragmentation and the codex decode had finished. Two exit paths
skipped it:

- `defragment_into` returning an error after some bytes had already
  been written into the buffer.
- A `Codex::decode` implementation panicking partway through the
  in-place decode.

In both cases the bytes already written stayed in the buffer until a
later `with_key` call on the same thread overwrote them.

The guard is now created before the first byte is written, so the
buffer is zeroed on success, on error and on unwind. Three new unit
tests in `src/vault/mod.rs` read the thread-local buffer after a
forced defragment error, a panicking codex (under `catch_unwind`) and a
panicking callback, and check that it is all zeros. The first two fail
against the 1.0.0 code.

The same pattern existed in two one-shot paths and is fixed the same
way:

- `StandardFragmenter`, `InterleavedFragmenter` and
  `RandomFragmenter::defragment` built their output in a plain
  `Vec<u8>` and wrapped it in a `RawKey` only on success. They now
  write into a `RawKey` from the start, so a partial result is zeroed
  on drop if defragmentation fails.
- The internal codex pass used by `KeyVault::fragment` and
  `KeyVault::defragment` collected into a plain `Vec<u8>`. It now
  transforms a `RawKey` in place, so the buffer is zeroed if a codex
  panics.

The scratch buffer design itself (thread-local, reused across calls)
is unchanged in this release.

### Changed: the `std` feature is required ([#3](https://github.com/jamesgober/key-vault/issues/3))

`src/lib.rs` declared `#![cfg_attr(not(feature = "std"), no_std)]`,
but the crate uses `std` types throughout (`HashMap`, `Mutex`,
`Instant`, `SystemTime`, `ThreadId`), and a build without `std` has
never compiled. 1.0.1 removes that attribute. Building without the
`std` feature now fails with one clear message:

```text
error: key-vault currently requires the `std` feature; no_std support is planned
```

The `std` feature is kept and stays on by default, so existing
`Cargo.toml` feature lists keep working. Doc comments that mentioned
future `no_std` builds, the feature table in `docs/API.md` and the
musl note in `docs/PLATFORM-NOTES.md` now say that `std` is required.

### Removed: unused `rand_core` dependency

`rand_core = "0.6"` was listed in `[dependencies]` but nothing in the
crate used it under any feature combination. Randomness comes from
`getrandom`. The dependency is removed; `docs/ARCHITECTURE.md` is
updated to match.

## Stability

- **Public API**: unchanged. `cargo semver-checks` against 1.0.0:
  222 checks pass, no semver update required.
- **Feature names**: unchanged. `std` remains a valid (and default)
  feature.
- **MSRV**: unchanged, 1.85 (edition 2024).

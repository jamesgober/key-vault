# v1.2.0: Lock Reporting, Bounded Failure Tracking, Nested Reads and Faster Writes

**Release date:** 2026-11-11
**Phase:** 1.2.0 (minor release)
**Status:** **stable.** The 1.0 contract in [`docs/STABILITY-1.0.md`](../STABILITY-1.0.md) holds; the public API only grows.

---

## Why this release exists

1.1 kept keys in page-locked memory as long as the OS allowed it, but
said nothing when it did not, and on Windows the default allowance ran
out after about a thousand keys. Failure reporting kept every reported
name forever and slowed down as failures for one name piled up. Two
reads nested inside each other panicked, a per-key lockout could be lost
when clears ran concurrently, every registry write copied the whole
registry, and threads reading one key contended on a shared counter.
1.2.0 fixes all of these without breaking changes.

---

## What's in 1.2.0

### Page-lock failures are reported, refusable and retried

```rust
use key_vault::KeyVaultBuilder;

let vault = KeyVaultBuilder::new().with_strict_locking(true).build();
// register / rotate return Error::MemoryLock instead of storing a key
// that the OS will not page-lock.

let status = vault.memory_status();
println!("{} of {} keys page-locked", status.locked, status.keys);
```

- `KeyVault::memory_status()`, `KeyVault::is_memory_locked(handle)`,
  `Fragments::is_locked()` and `Fragments::is_excluded_from_dumps()`
  read the current state of a key's pages.
- `SecurityMonitor::on_memory_lock_failure` (default no-op) fires when a
  key is stored unlocked, once per run of failures; `LogMonitor` logs it.
- The page pool records each page's lock state, hands out blocks on
  locked pages first and retries pages that failed, so raising the limit
  at run time helps keys registered afterwards.
- On Windows, when `VirtualLock` runs out of quota the crate raises its
  own process's working-set size (at least 1 MiB at a time, at most
  256 MiB in total). 5,000 keys in a default process are now all locked;
  in 1.1 at least three quarters of them were not.
- After `fork`, the child's next vault call locks the pool and heap pages
  again, and a page-protected key is locked again on its first read in
  the child. In 1.1 a forked child held every key unlocked.
- Pool memory is mapped, locked and excluded from dumps 16 pages at a
  time, so Windows Error Reporting's 512-block limit covers 16 times as
  much pool memory.

See [`docs/PLATFORM-NOTES.md`](../PLATFORM-NOTES.md) for each platform's
limit and how to raise it.

### Bounded failure tracking

`report_failure` is safe to call with names from untrusted input:

- nothing is recorded while both lockout thresholds are off (the
  default);
- with a threshold on, each name keeps at most 64 slots, names of
  registered keys and the master credential are always tracked, other
  names share a fixed capacity (`with_failure_tracking_capacity`,
  default 4096) with the idlest forgotten first, names are stored as
  keyed hashes, and the tracker is split into sixteen shards;
- per-key lockout counts only names a key is registered under, and
  unregistering a key drops its lockout and failure history.

A million distinct names used to add 234 MiB that was never returned;
now nothing. After 160,000 failures for one name a report took 137 µs
(Windows) to 164 µs (Linux) under one global lock; now about 30 to 60 ns.

`report_failure_with_note(name, note)` takes a note built at run time.

### Per-key lockout state

Each registered key carries its own lockout word, replacing a map of
lockouts plus a separate count of its entries. Concurrent
`clear_key_lockout`, `clear_lockout` and new lockouts can no longer
leave a locked-out key readable. A test drives the exact interleaving
that did so in 1.1.

### Nested `with_key`

```rust
let both = vault.with_key(kek, |kek| vault.with_key(dek, |dek| unwrap(kek, dek)))??;
```

The inner call reassembles into a locked buffer of its own, wiped when
it returns. In 1.1 it panicked.

### Registry writes and reads

The registry snapshot is a persistent hash trie. `register`, `rotate`
and `unregister` copy one path instead of the whole map, and the
duplicate-name check and `handle_for_name` are hashed lookups. With
20,000 keys registered, `register` went from 4.2 ms to 7.8 µs on Linux
and from 12 ms to 7.5 µs on Windows.

`with_key` reads the key under the registry snapshot without taking a
reference count, then releases the snapshot before the callback runs. In
1.1 each read cloned the key storage's `Arc`, so every thread reading one
key wrote to the same counter.

### Smaller fixes

- `RandomFragmenter` reserves its layout buffer up front; growing it by
  reallocation left unwiped partial layouts in freed heap memory.
- Decoy chunks take the sizes of real chunks. With a wide chunk range
  they could be far larger than the key.
- A failed re-seal of a page-protected key is retried once.
- `KeyVault::new()`, `KeyVault::builder()` and `Default for KeyVault`.
- `benches/concurrent_access.rs` measures reads with threads started
  once and released by a barrier.
- The docs that pointed at the crate-private `LockedBytes::is_locked()`,
  claimed uncontended concurrent reads and nanosecond rotation swaps, or
  said failed pool locks were retried, now match the code.
  `docs/SECURITY.md` also covers the codex's cache-timing exposure and
  page protection for continuously read keys.

### Behaviour changes to know about

- `FailureContext::consecutive_failures` is `1` (and `window_elapsed`
  zero) when no threshold is on, since nothing is recorded.
- Failures for a name no key is registered under no longer count toward
  the per-key lockout, and a key registered later under that name starts
  clean.
- `KeyVault`'s `Debug` output counts locked-out keys by walking the
  registry.
